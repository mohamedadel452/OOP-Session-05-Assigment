1) Object Copying

أولاً: من الصفر

لما تكتب b = a الـ C# بتنسخ اللي جوه المتغير. لو المتغير value type (int, struct) اللي جواه هو القيمة نفسها، فبتتعمل نسخة مستقلة. لو reference type (class) اللي جواه هو عنوان الـ object على الـ Heap، فبيتنسخ العنوان بس والاتنين يشاوروا على نفس الـ object.

int a = 10; int b = a; b = 20;          // a = 10 (نسخة مستقلة)
var p1 = new Person { Name = "Ahmed" };
var p2 = p1;                            // نفس الـ object
p2.Name = "Omar";
Console.WriteLine(p1.Name);             // Omar

ثانياً: Shallow Copy

بتعمل object جديد وبتنسخ حقوله واحد واحد. الحقول من نوع value بتتنسخ بقيمتها، والحقول من نوع reference بيتنسخ عنوانها، فالنسختين بيشاركوا نفس الـ objects الداخلية.

public class Address { public string City { get; set; } }
public class Person
{
    public string Name { get; set; }
    public int Age { get; set; }
    public Address Address { get; set; }

    public Person ShallowCopy() => (Person)MemberwiseClone();
}

var p1 = new Person { Name = "Ahmed", Age = 25, Address = new Address { City = "Cairo" } };
var p2 = p1.ShallowCopy();
p2.Age = 30;               // p1.Age يفضل 25
p2.Address.City = "Giza";  // p1.Address.City بقت Giza !

الميكانيزم: MemberwiseClone دالة protected في System.Object. بتخصص object جديد بنفس النوع وبتنسخ الـ bytes بتاعة الحقول، من غير ما تشغّل أي constructor.

ثالثاً: Deep Copy

بتعمل نسخة جديدة من الـ object ومن كل الـ objects اللي بيشاور عليها، فالنسخة مستقلة تماماً. فيه ثلاث طرق:

الطريقةالميزةالعيب
يدوي (Copy constructor أو DeepCopy)تحكم كامل وأسرعلازم تحدّثه كل ما تضيف حقل (بيتنسى بسهولة)
Serialization (JSON)سطر واحدبطيء، بيفقد private fields والـ polymorphism، وبيتعثر مع الـ cycles
ICloneableموجود في الـ BCLالـ contract غامض (deep ولا shallow؟) ويرجع object
// يدوي
public Person DeepCopy() => new Person
{
    Name = Name, Age = Age,
    Address = new Address { City = Address.City }
};

// Serialization
static T DeepClone<T>(T src) =>
    JsonSerializer.Deserialize<T>(JsonSerializer.Serialize(src))!;

رابعاً: متقدم وأخطاء شائعة

1) الـ struct مش دايماً "قيمة بالكامل":

struct S { public int[] Arr; }
var a = new S { Arr = new[] { 1 } };
var b = a;           // نسخة من الـ struct
b.Arr[0] = 99;
Console.WriteLine(a.Arr[0]);   // 99

الـ struct بيتنسخ بالقيمة، لكن لو جواه حقل reference فالعنوان هو اللي بيتنسخ. جدول السلايد 10 بيقول "struct → actual values copied" وده ناقص.

2) الـ with في الـ record هي Shallow Copy:

record Order(string Id, List<string> Items);
var a = new Order("1", new() { "x" });
var b = a with { Id = "2" };
b.Items.Add("y");
Console.WriteLine(a.Items.Count);   // 2 : نفس الـ List

3) الـ string: reference type بس immutable، فمشاركته مفيهاش خطر (أي تعديل بيعمل string جديد). عشان كده في الـ deep copy بتنسخه بالـ reference عادي. السلايد 15 بيحطه مع "new objects"، والفرق ده مهم.

4) الـ Collections: new List<Person>(list) بتعمل list جديدة لكن بنفس الـ Person objects، يعني Shallow. لازم list.Select(p => p.DeepCopy()).ToList().

5) BinaryFormatter (مذكور في السلايد 16): ممنوع تستخدمه. بيسبب ثغرات Remote Code Execution، واتعلّم obsolete وبقى يرمي exception في .NET 9 فما فوق. استخدم System.Text.Json أو كتابة يدوية.

الـ Cycles: لو Parent فيه Child والـ Child فيه Parent، الـ deep copy اليدوي البسيط هيدخل في recursion لا نهائي (StackOverflow)، والـ JSON هيرمي exception إلا لو فعّلت ReferenceHandler.Preserve. الحل: dictionary بيتتبع اللي اتنسخ قبل كده.

إمتى أي واحدة؟ الـ shallow لو كل الحقول value types أو immutable. الـ deep لو هتعدّل النسخة وعايز الأصل ما يتأثرش. وبديل أفضل في كتير من الحالات: Immutable objects (records و init) فمفيش حاجة تتنسخ أصلاً.

2) Static

أولاً: من الصفر

العضو العادي (instance) بيتبع object معين، وكل object ليه نسخته. العضو الـ static بيتبع الـ class نفسه وفيه نسخة واحدة بس مشتركة. بتناديه باسم الـ class مش باسم object.

public class Counter
{
    public static int Count = 0;      // مشترك بين كل الـ objects
    public string Name;               // لكل object نسخته

    public static void ShowCount() => Console.WriteLine($"Count = {Count}");
    public void Increment() => Count++;   // instance يقدر يوصل لـ static
}

var c1 = new Counter(); var c2 = new Counter();
c1.Increment(); c2.Increment();
Counter.ShowCount();     // Count = 2

ثانياً: القواعد وليه موجودة

StaticInstance
يخص الـ classيخص الـ object
نسخة واحدةنسخة لكل object
بتناديه بـ ClassName.Memberبتناديه بـ object
ما يقدرش يوصل لـ instance مباشرةيقدر يوصل للاتنين

ليه الـ static مش بيقدر يوصل لـ instance member؟ لأن مفيش this. الدالة الـ static بتتنادى من غير object، فالـ compiler مش عارف حقل Name بتاع أنهي object. ولنفس السبب مفيش this ولا base جوه static context.

ثالثاً: Static Constructor و Static Class

public static class AppConfig
{
    public static string AppName { get; }
    static AppConfig() { AppName = "MyApp"; }   // مفيش access modifier ولا parameters
}
  • الـ static constructor بيشتغل مرة واحدة قبل أول استخدام للـ class، والـ runtime بيضمن إنه thread-safe.
  • الـ static class: مينفعش instance منه، ومينفعش يورّث، وكل أعضاؤه لازم static. في الـ IL بيتعلّم abstract sealed.
  • مناسب لـ: Math، دوال مساعدة من غير state، والـ constants.

رابعاً: مشاكل الإنتاج والمتقدم

1) Race condition: في تطبيق ويب الـ static مشترك بين كل الـ requests (threads).

public static class Stats { public static int Hits; }
Parallel.For(0, 100_000, _ => Stats.Hits++);
Console.WriteLine(Stats.Hits);     // أقل من 100000 غالباً
// الحل:
Parallel.For(0, 100_000, _ => Interlocked.Increment(ref Stats.Hits));

السبب إن ++ مش عملية واحدة: قراءة ثم زيادة ثم كتابة، والـ threads بتتداخل.

2) فشل الـ static constructor دايم:

static class Db {
    public static readonly string Conn;
    static Db() { Conn = Environment.GetEnvironmentVariable("CONN")
                         ?? throw new Exception("missing"); }
}
// أول استخدام: TypeInitializationException
// وكل استخدام بعده بيرمي نفس الخطأ حتى إعادة تشغيل الـ process

3) لكل نوع generic نسخة static:

class Cache<T> { public static int Hits; }
Cache<int>.Hits++;
Console.WriteLine(Cache<string>.Hits);   // 0

4) تسريب الذاكرة: الحقول الـ static هي GC roots، فأي object محفوظ في static List أو static event عمره عمر الـ process ومش بيتنضف. وكمان الـ static بيصعّب الاختبار (state مشترك بين الـ tests ومفيش mock)، فللـ dependencies استخدم DI بدل static.

ملحوظة دقة: السلايد 24 بيقول إن الـ static "يعيش طول عمر التطبيق"، وده صح عملياً، لكن التحديد الأدق: بيعيش طول عمر الـ type المحمّل (وفي الـ plug-ins اللي بتتحمّل في AssemblyLoadContext منفصل ممكن يتفرغ).

3) Extension Methods

أولاً: من الصفر

عايز تضيف دالة لنوع مش بتاعك (string مثلاً) ومينفعش تعدّل كوده. الـ extension method بتخليك تكتب text.Shout() كأنها جزء من string.

public static class StringExtensions            // 1) static class
{
    public static string Shout(this string s)   // 2) static method + this على أول parameter
        => s.ToUpper() + "!";
}
"hello".Shout();     // HELLO!

ثانياً: الميكانيزم (الأهم)

مفيش حاجة اتضافت للنوع. الـ compiler وقت الترجمة بيحوّل name.Shout() إلى StringExtensions.Shout(name). يعني syntactic sugar لدالة static. وده سبب إن النداء على null بيشتغل:

string? name = null;
bool r = name.IsNullOrEmptyEx();   // true ، مفيش NullReferenceException
public static bool IsNullOrEmptyEx(this string? s) => string.IsNullOrEmpty(s);

الـ NRE بتحصل جوه الدالة لو استخدمت s.Length على null، مش في مكان النداء، وده بيربك الـ stack trace.

ثالثاً: قواعد الـ Resolution

  • الـ instance method دايماً بتكسب على الـ extension لو الاسم والـ signature متطابقين، والـ extension مش بتعمل override.
  • لازم الـ namespace يتعمله using، ودي الطريقة اللي بتشتغل بيها LINQ (using System.Linq).
  • ما تقدرش توصل لـ private/protected لأنها دالة خارجية.
class Foo { public void Hi() => Console.WriteLine("instance"); }
static class FooExt { public static void Hi(this Foo f) => Console.WriteLine("extension"); }
new Foo().Hi();    // instance

أخطاء ومخاطر:

  1. Value types بتتنسخ: 
    static void Inc(this int x) { x++; }
int n = 5; n.Inc();
Console.WriteLine(n);   // 5 : عدّلت النسخة
  2. الـ Versioning: لو نوع المكتبة أضاف لاحقاً instance method بنفس اسم extension بتاعتك، النداءات القديمة هتتحول بصمت للـ instance method من غير أي تحذير.
  3. تلوث الـ IntelliSense: extension على object أو string بتظهر في كل مكان. اعملها في namespace مخصص.

الاستخدام الأقوى: الـ extension على الـ interface زي IEnumerable<T> (كل LINQ) والـ IServiceCollection (كل AddXxx() في ASP.NET Core). بتضيف سلوك لكل الأنواع اللي بتنفذ الـ interface من غير ما تلمسها.

إمتى ما تستخدمهاش (السلايد 36): لو الدالة محتاجة وصول للـ private، أو بتخالف مسؤولية النوع، أو أنت مالك النوع فحطها فيه مباشرة. وفي C# 14 اتضافت صيغة extension blocks اللي بتدعم properties وغيرها، راجع الـ docs قبل ما تعتمد عليها.

4) Partial

أولاً: من الصفر

الـ partial بتخليك تكتب نفس الـ class في أكتر من ملف. الـ compiler بيجمعهم كلهم في class واحدة قبل ما يترجم.

// Student.Core.cs
public partial class Student { public int Id { get; set; } public string Name { get; set; } }

// Student.Extras.cs
public partial class Student { public void Display() => Console.WriteLine($"{Id} - {Name}"); }

ليه موجودة؟ أساساً لفصل الكود المولَّد تلقائياً (Designer و EF scaffolding و Source Generators) عن كودك. الأداة تعيد توليد ملفها وكودك في ملف تاني ما يتمسحش.

ثانياً: Partial Methods

public partial class Logger
{
    partial void WriteLog(string message);          // declaration
    public void Log(string m) { WriteLog(m); }
}
public partial class Logger
{
    partial void WriteLog(string message) => Console.WriteLine($"LOG: {message}");  // اختياري
}

الـ partial method التقليدية: void وضمنياً private، ولو مفيش implementation الـ compiler بيشيل النداء تماماً. من C# 9 ظهرت extended partial methods (بـ access modifier أو return value أو out) وفي الحالة دي الـ implementation إجبارية.

ثالثاً: القواعد والمتقدم

  • كل الأجزاء: كلمة partial، نفس الـ namespace، نفس الـ assembly، ونفس الـ accessibility لو اتحددت.
  • وقت الـ Runtime مفيش حاجة اسمها partial، دي class عادية وواحدة.
  • الـ partial ممكن على class و struct و interface.
  • الـ base class والـ interfaces بيتجمعوا من كل الأجزاء.
// مثال حديث: Source Generator في .NET
public static partial class Patterns
{
    [GeneratedRegex(@"^\d{3}$")]
    public static partial Regex ThreeDigits();   // الـ generator يكتب الجسم
}

خطر عملي: لو عدّلت يدوياً في الملف المولَّد (*.Designer.cs أو *.g.cs) هتضيع تعديلاتك عند إعادة التوليد. حط كودك في الجزء التاني دايماً. وكمان استخدام partial لتقسيم class ضخمة بدون سبب بيخبي مشكلة تصميم (God class) ولا يحلها.

5) تصحيحات للسلايدات

  1. سلايد 37: الإجابة المكتوبة B (False) غلط. الكود بيرجع true (الـ null بيعتبر فاضي)، فالصح A. شرح السلايد نفسه بيقول "returns true" وبيتناقض مع الحرف.
  2. سلايد 46: سؤال 8 متكرر من الجلسة السابقة بإجابة C، والصح A (الخطأ CS0534 عند تعريف class Employee).
  3. سلايد 45: "Partial classes can't be nested inside other classes" غلط. الـ nested partial مسموح (والـ class الخارجية تحتاج partial فقط لو هي نفسها مقسمة). و"can't inherit in one part and define base in another" مضللة: تقدر تحدد الـ base في جزء واحد بس، والمهم ما يحصلش تعارض بين الأجزاء.
  4. سلايد 16: BinaryFormatter ممنوع (قسم 1).
  5. سلايد 10 و 15: الـ struct اللي فيه references، والـ string، زي ما اتشرح.
